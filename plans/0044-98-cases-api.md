# #98: Cases API, and case scope on ask

## Context

#97 (PR #194, merged to `staging` as `febcebd`) put cases into api.v1: `/cases` CRUD plus archive/unarchive, `PATCH /conversations/{id}` to save a conversation to a case, and a `caseId` filter on the conversation list. `apps/api` serves none of it yet: `POST /conversations` still answers 400 for any `caseId` (`src/routes/conversations.ts:99`), the ask route sends `allowedCaseIds: []` (`:172`), `app.conversations.case_id` has no FK (`src/db/schema.ts:173`), and there is no `app.cases` table.

This is the second step of roadmap item A7 (contract → **API** → web). Issue text: "Implement the cases contract, owner only (FR-AUTH-4). Accept `caseId` on conversations and send `allowedCaseIds: [caseId]` in the scope. Add the marker-document isolation test (SEC-8)."

**Requirements:** FR-CASE-1, FR-CASE-5, FR-CASE-6, FR-AUTH-4, FR-AUTH-5, SEC-8.

## Decisions

- **Table `app.cases`** (migration `0011_cases`, generated by `pnpm db:generate` from `schema.ts`, with a hand-written `.down.sql` as ADR-0007 requires): `id`, `owner_user_id` → users (cascade), `account_id` → accounts (cascade), `title text not null`, `court`, `case_number`, `case_type`, `status`, `judge`, `assigned_lawyer`, `summary` (all `text` null), `filed_on` and `next_hearing_on` (`date` null), `parties jsonb not null default '[]'` with a check `jsonb_typeof(parties) = 'array'`, `relevant_laws text[] not null default '{}'`, `archived_at timestamptz null`, `created_at`, `updated_at`. Index `cases_owner_updated_idx (owner_user_id, updated_at)` for the cursor list, like conversations.
- **FK `conversations.case_id → cases.id ON DELETE SET NULL`.** Cases are never deleted through the API (archive only), so the rule is only for operator cleanup. The schema comment "no FK until cases land" goes.
- **No FK on `ai_audit_records.case_id`.** The table is append-only (trigger from 0004 rejects any UPDATE except the conversation-FK set-null), so an `ON DELETE SET NULL` would raise and `RESTRICT` would stop operator cleanup. An audit row is a record of what the request carried, not a live reference. Documented in the schema comment.
- **Parties are stored as jsonb** `[{ side, name, label? }]` and `relevantLaws` as `text[]`; the DTO passes them through. Validation happens in zod, not in SQL (apart from the array-type check).
- **Validation mirrors the contract with `z.strictObject`**, as `settings.ts` does: `title` trimmed 1–200; the nullable strings trimmed with their max lengths (`court` 120, `caseNumber` 80, `caseType` 80, `status` 80, `judge` 200, `assignedLawyer` 120, `summary` 4000); `filedOn` and `nextHearingOn` `z.iso.date()`; `parties` ≤ 50 of `strictObject { side: enum, name 1–200, label ≤ 40 optional }`; `relevantLaws` ≤ 50 trimmed strings 1–120. `CaseUpdate` is the same with every field optional and nullable where the contract allows, plus `.refine(at least one key)`. An empty trimmed string for a nullable field becomes `null` (so the web can send a cleared input either way).
- **Archive is idempotent**: `archive` sets `archived_at = coalesce(archived_at, now())`, `unarchive` sets it null; both return the row and 404 if it isn't the caller's.
- **`listCases` state filter**: `active` (default) is `archived_at IS NULL`, `archived` is `IS NOT NULL`, `all` is no filter. Order `updated_at desc, id desc`, cursor as in the other stores.
- **Cursor helpers are shared.** `encodeCursor` / `decodeCursor` are copied today in `conversations/store.ts` and `admin/store.ts`. They move to `src/lib/cursor.ts` and all three stores use it (a small, safe refactor; the 400 on a bad cursor is unchanged).
- **The case rule for conversations** (contract: the caller's **active** case, else 400 with `errors[].path = "caseId"`) lives in one helper, `requireActiveCase(db, owner, caseId)`, used by `POST /conversations` and `PATCH /conversations/{id}`. An archived or foreign case is a 400, never a 404, so nothing is revealed about other users' ids.
- **`PATCH /conversations/{id}`** sets `case_id` and bumps `updated_at` (saving research to a case is activity, so it moves up the list; FR-RES-8 "most recently active").
- **Ask scope** becomes `allowedCaseIds: conversation.caseId ? [conversation.caseId] : []`. `case_id` can only be set through the ownership-checked paths and a case never changes owner, so no re-check at ask time. An archived case still scopes its conversation's later questions (it is still the caller's).
- **SEC-8 / FR-CASE-6 at the API level**: the api's part of the isolation guarantee is that the scope it signs never names a case the caller doesn't own. The DB-level marker test (a marker chunk in another user's case is never retrieved) already exists in `services/ai/tests/test_retrieval.py` (#19). Here the tests prove: a conversation saved to Alice's case sends exactly `[thatCaseId]`; an unscoped one sends `[]`; Bob cannot attach Alice's case (400) nor read it (404); the audit record carries the `case_id`. Documented in the plan and the test names.
- **`GET /sources/{id}`** stays as it is. Its comment says private case documents must be limited to the scope "with cases"; documents don't exist until #100/#101, so the comment is updated to point at #101 instead.
- **Roadmap note** on A7 changes from "the API rejects `caseId` with 400 until cases exist" to "API done (#98); `/cases` is `ComingSoon` until #99".

Branch: `feature/cases-api` (already cut from `staging` at `febcebd`). PR title: `feat(api): cases, and case scope on ask (FR-CASE-1, FR-CASE-5, FR-CASE-6)`.

## Changes

1. **`apps/api/src/db/schema.ts`**: `cases` table as above; `conversations.caseId` gets `.references(() => cases.id, { onDelete: "set null" })`; comments updated; `export type Case`, `NewCase`.
2. **`apps/api/drizzle/0011_cases.sql`** + `meta/0011_snapshot.json` + `_journal.json` from `pnpm db:generate` (no DB needed; it diffs against `meta/0010_snapshot.json`). Add a header comment to the SQL like 0010's. Hand-write **`0011_cases.down.sql`**: drop the conversations FK, drop `app.cases`.
3. **`apps/api/src/lib/cursor.ts`** (new): `encodeCursor`, `decodeCursor` (moved from `admin/store.ts` and `conversations/store.ts`, which import it).
4. **`apps/api/src/cases/store.ts`** (new): `listCases(db, owner, { state, cursor, limit })`, `createCase(db, owner, fields)`, `findOwnCase(db, owner, id)`, `updateCase(db, owner, id, patch)` (returns undefined when not owned; sets `updated_at = now()`), `setArchived(db, owner, id, archived)`, `requireActiveCase(db, owner, caseId)` (throws the 400 `HttpProblem` with `errors[]`).
5. **`apps/api/src/routes/cases.ts`** (new): zod `caseInput`, `caseUpdate`, `listQuery` (`state` enum default `active`, `cursor`, `limit` as in conversations); `toCaseDto` (dates as `YYYY-MM-DD` strings, timestamps ISO, `archivedAt` null or ISO); the six routes under `requireAuth`. 404 helper like `conversations.ts`.
6. **`apps/api/src/app.ts`**: mount `casesRouter({ db: deps.orm, jwtSecret })`.
7. **`apps/api/src/conversations/store.ts`**: `createConversation` takes `caseId`; `listConversations` takes an optional `caseId` filter; new `updateConversationCase(db, owner, id, caseId | null)`.
8. **`apps/api/src/routes/conversations.ts`**: `pageQuery` gains `caseId: z.uuid().optional()`; `POST` calls `requireActiveCase` when `caseId` is given; new `PATCH /conversations/:conversationId` with `z.strictObject({ caseId: z.uuid().nullable() })` → 200 summary; ask scope uses the conversation's `caseId`; the "until cases land" comments go.
9. **`apps/api/src/routes/sources.ts`**: comment points at #101.
10. **Tests**
    - **`apps/api/test/cases.test.ts`** (new, `describe.skipIf(!url)`, same harness as `settings.test.ts`): create with every field and with only `title` (defaults `null` / `[]`), each contract-checked; 400 for an unknown field, a bad date, an empty title, 51 parties, an empty PATCH body; GET 404 for Bob and for a non-uuid; list order, `state` filter, pagination; PATCH partial, `null` clears, `[]` clears, `updatedAt` moves; archive and unarchive idempotent and hidden/shown by `state`; 401 without a token.
    - **`apps/api/test/conversations.test.ts`**: replace "400 for a caseId until cases exist" with: 201 with own active case (`caseId` in the body); 400 with Bob's case, an archived case and an unknown id (contract-checked, `errors[0].path === "caseId"`); `PATCH` attach then detach (contract-checked) and 404 for Bob's conversation; list `?caseId=` returns only that case's conversations and an empty page for Bob's case id; the scope test asserts `allowedCaseIds: [caseId]` for a case conversation and `[]` otherwise (SEC-8); the audit test checks `case_id`.
    - **`apps/api/test/migrations.test.ts`**: `cases` in the table list; the down/up chain includes `0011_cases`.
11. **Docs**: `apps/api/README.md` route table (six case rows; the conversation rows lose "waits for cases"; the scope sentence under "The AI call"); `CHANGELOG.md` Added entry; `docs/engineering/stream-a-roadmap.md` A7 note; `plans/0043-97-cases-contract.md` status → Done (merged as #194); new `plans/0044-98-cases-api.md` (this plan, repo status line).

## Verification

- Tests need Postgres as `caseguard_app`. Locally the Docker DB is down and has no `caseguard_test` database, so: `pnpm db:up`, then inside the container create `caseguard_test` and run `infra/db/sql/bootstrap.sql` against it with the `.env` passwords (the same two commands CI runs), then
  `APP_TEST_DATABASE_URL=postgresql://caseguard_app:<APP_DB_PASSWORD>@127.0.0.1:5433/caseguard_test pnpm --filter ./apps/api test` (`127.0.0.1`, not `localhost`, per the IPv6 quirk). The tests `TRUNCATE app.accounts CASCADE`, so they must never point at the `caseguard` dev database.
- `pnpm db:generate` run a second time produces nothing (the snapshot matches the schema).
- `pnpm --filter ./apps/web run typecheck` still passes (the web only consumes the contract types; nothing changes for it).
- Push, open the PR against `staging`, wait for `ci-ok` (the `api` job runs the DB tests against a bootstrapped Postgres). Merging needs the user's explicit go-ahead (`--squash`, never `--delete-branch`).

## Notes from implementation

- `0011_cases.down.sql` also sets `conversations.case_id` to null, so a later up can add the FK again.
- `listConversations` declares no 400 in api.v1 (a bad cursor or `caseId` is a 400 already). The test checks the status only; adding `"400"` to the operation is a follow-up contract PR.
