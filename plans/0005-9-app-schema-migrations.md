# #9: Drizzle migrations for the `app` schema, plus `users` and `accounts`

## Context
`apps/api` has no tables and no migration tool. `apps/api/README.md` leaves the choice to "the first PR that creates tables", and PRD §14.2 allows "Prisma or Drizzle" for `app`. Issue #9 asks for three things: pick the tool, record it in an ADR, and create `users` and `accounts` with the FR-AUTH-5 ownership model (`owner_user_id`/`account_id` on owned rows).
**Done when:** migrations run as `caseguard_app` and are reversible, and the ADR is merged.
Auth (#10) builds on this later and is out of scope here.

**Decision:** Drizzle (chosen in this session).

Branch `feature/api-app-schema-migrations` off `staging`. PR title: `feat(api): Drizzle migrations for the app schema with users and accounts`.

## Changes
1. **Plan record** `plans/0005-9-app-schema-migrations.md`, a copy of this plan with the line `> **Status:** In progress · **Issue:** #9 · **PR:** #N`.
2. **ADR** `docs/adr/0007-drizzle-for-app-schema.md`, following `docs/adr/0000-template.md`:
   - Why Drizzle: SQL-first, runs on the existing `pg` Pool, has no generated client or binary engine, and is TypeScript-native.
   - PRD §14.2 allows one migration tool per schema.
   - Migrations run as the schema owner `caseguard_app` (ADR-0002). Drizzle's bookkeeping table lives in `app` (`migrationsSchema: "app"`), because `caseguard_app` can't create schemas.
   - Reversibility comes from a hand-written `NNNN_*.down.sql` next to each generated migration. A migration PR without one fails review, and a test enforces it.
3. **Dependencies** (`apps/api/package.json`): add `drizzle-orm` and dev dependency `drizzle-kit`.
   - Scripts: `db:generate` (`drizzle-kit generate`), `db:migrate` (`tsx src/db/migrate.ts up`), `db:migrate:down` (`tsx src/db/migrate.ts down`).
   - Root `package.json`: forward `db:migrate`, next to the existing `db:bootstrap`.
4. **`apps/api/drizzle.config.ts`**: `dialect: "postgresql"`, `schema: "./src/db/schema.ts"`, `out: "./drizzle"`, `schemaFilter: ["app"]`, `migrations: { schema: "app" }`, `dbCredentials.url` from `API_DATABASE_URL`.
5. **`apps/api/src/db/schema.ts`**, using `pgSchema("app")`:
   - `accounts`:
     - `id uuid pk default gen_random_uuid()`
     - `kind text not null default 'individual'` with check `kind in ('individual')`. Tenants come in P2 (PRD §2), and widening the check then is a one-line migration.
     - `created_at timestamptz not null default now()`
   - `users`:
     - `id uuid pk default gen_random_uuid()`
     - `account_id uuid not null references accounts(id) on delete cascade`
     - `email text not null`, with a **unique index on `lower(email)`** (there's no citext extension, and bootstrap only creates vector and pg_trgm)
     - `password_hash text not null`
     - `name text not null`
     - `role text not null default 'user'` with check `role in ('user','admin')` (FR-AUTH-2 says a role outside the set is rejected)
     - `locale text not null default 'en'` with check `locale in ('en','ur')`
     - `ai_enabled boolean not null default true` (FR-AUTH-3)
     - `created_at`, `updated_at timestamptz not null default now()`
     - an index on `account_id`
   - A header comment states the FR-AUTH-5 rule: every future owned table carries `owner_user_id → users(id)` and `account_id → accounts(id)`.
   - Export the inferred `User`/`Account` row types.
6. **`apps/api/src/db/client.ts`**: `createDb(pool: Pool)` returns `drizzle(pool, { schema })`, and the file exports `type Db`. It's not wired into `createApp` yet; #10 does that.
7. **`apps/api/src/db/migrate.ts`**: our own small runner, because drizzle-orm's `migrate()` always runs `CREATE SCHEMA IF NOT EXISTS`. Postgres checks database CREATE privilege for that first, and `caseguard_app` doesn't have it. The runner keeps drizzle's bookkeeping format and reads files with `readMigrationFiles`. It exports `migrateUp(pool, folder)` and `migrateDown(pool, folder)` for tests, plus a CLI entry point that reads `API_DATABASE_URL` and logs through the pino logger (`no-console`).
   - `up`: under an advisory lock in one transaction, apply each journal entry newer than the last applied row in `app.__drizzle_migrations`.
   - `down`: read the newest row of `app.__drizzle_migrations` and map it to its tag through `drizzle/meta/_journal.json`. In one transaction, run `drizzle/<tag>.down.sql` and delete that row. If nothing is applied, do nothing and log it.
   - The migrations folder resolves relative to the module, so it works from both `src/` (tsx) and `dist/` (Docker).
8. **Migration files**:
   - `drizzle/0000_users_accounts.sql` and the `meta/` folder, generated by `pnpm db:generate`. Remove the generated `CREATE SCHEMA "app"`, because bootstrap owns the schema.
   - `drizzle/0000_users_accounts.down.sql`, hand-written: `DROP TABLE app.users; DROP TABLE app.accounts;`.
9. **Docker** (`apps/api/Dockerfile`): copy `apps/api/drizzle` to `/app/drizzle`. Change the CMD to `sh -c "node dist/db/migrate.js up && node dist/server.js"`, so `docker compose up` (and the CI `stack` job) has the tables. The api container already connects as `caseguard_app`.
10. **CI** (`.github/workflows/ci.yml`, `api` job):
    - Before `test`, add a step that runs `psql "$DATABASE_URL" -v ON_ERROR_STOP=1 -v app_pw=caseguard_app -v ai_pw=caseguard_ai -f infra/db/sql/bootstrap.sql`. psql is preinstalled on ubuntu-latest.
    - Add the env var `APP_TEST_DATABASE_URL: postgresql://caseguard_app:caseguard_app@localhost:5432/caseguard_test`. The tests connect as the real app role, which proves the "runs as `caseguard_app`" requirement.
11. **Tests** in `apps/api/test/migrations.test.ts`, inside `describe.skipIf(!process.env.APP_TEST_DATABASE_URL)`:
    - `up` creates `app.accounts`, `app.users` and `app.__drizzle_migrations`, owned by `caseguard_app` (checked through `pg_tables.tableowner`).
    - The table owner is `current_user`, which shows the role running migrations owns them.
    - Constraints: duplicate email in a different case gives `23505`; `role = 'superuser'` gives `23514`; an unknown `locale` gives `23514`; deleting an account cascades to its users.
    - `down` then `up` round-trips: the tables are dropped, then recreated, and the journal row count goes back up.
    - Every entry in `_journal.json` has a matching `.down.sql` file. This guard needs no DB and always runs.
    - Clean up with `migrateDown` back to empty in `afterAll`.
12. **Docs**:
    - `apps/api/README.md`: replace the "Stream A's choice" note with the migration workflow (edit `schema.ts`, run `db:generate`, write the `.down.sql`, run `db:migrate`).
    - `docs/engineering/local-setup.md`: run `pnpm db:migrate` after `pnpm db:bootstrap`.
    - `CHANGELOG.md` `[Unreleased]`: an "Added" entry.
    - PRD IDs for the PR body: FR-AUTH-5, ADR-0002.

## Verification
1. Database, roles and schemas: `docker compose up -d db`, then `pnpm db:bootstrap`.
2. Migrate up and check the tables: `pnpm db:migrate`, then `\dt app.*` in psql as `caseguard_app`.
3. Round-trip: `pnpm --filter ./apps/api db:migrate:down` drops the tables, then `pnpm db:migrate` recreates them.
4. Lint, typecheck and tests: `pnpm --filter ./apps/api lint`, `pnpm --filter ./apps/api typecheck`, and `APP_TEST_DATABASE_URL=postgresql://caseguard_app:<pw>@localhost:5432/caseguard pnpm --filter ./apps/api test`.
5. Full stack: `docker compose up --build` gives a healthy api, and the tables exist.
6. The PR passes CI: `api`, `stack` and `ci-ok` all green.
