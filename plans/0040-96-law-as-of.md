# #96: "law as of" date (FR-RES-11)

## Context

`lawAsOf` was already accepted end to end: in the api's ask body, the audit record (`law_as_of`), the AI client and `AnswerRequest`. But `research_answer` never passed it into `Question`, so it was ignored. No curated statute versions exist yet (FR-TEMP-* is a later module), so the honest scope ([handoff §3](../docs/engineering/handoff-res8-set2-res11.md#3-law-as-of-date-fr-res-11-96)) is to leave out judgments decided after the date, keep statutes as they are, and say so in a note on the answer.

## Decisions

- **The filter is inside the SQL**, in the corpus branch of both `_DENSE` and `_SPARSE`, before their `LIMIT`. Filtering afterwards would silently return fewer passages. Each branch joins `corpus.documents d` and adds `CAST(:as_of AS date) IS NULL OR d.kind <> 'judgment' OR d.decided_on IS NULL OR d.decided_on <= CAST(:as_of AS date)`.
  - Judgments with no known `decided_on` stay in, and so do statutes.
  - `as_of` is bound as `NULL` without a date, so the predicate is always true and the results are the same as before.
- **HNSW and the filter.** pgvector applies a `WHERE` to the neighbours the HNSW index already found (about `hnsw.ef_search`, 40 by default), so a date could still return fewer than k. With a date, `dense_search` turns on `hnsw.iterative_scan = strict_order` (pgvector 0.8, in the `pgvector/pgvector:pg17` image) for that one query, transaction-local, and turns it off again afterwards. On a 4,000-chunk synthetic corpus with the index forced, a restrictive date returned 47 rows without it and 50 with it. Undated queries keep today's settings.
- **`asOfNote`** is optional on ai.v1 `Answer` and api.v1 `Message` (assistant only). It is written in the answer's language (en, ur, roman_ur) and given on unanswerable answers too. It says that judgments decided after the date were left out, and that statute text is the current version, because historical versions aren't curated yet.
- **Storage.** `app.messages.as_of_note text NULL`, migration **0009**. Number 0008 is reserved for the lead's roles migration, which isn't merged yet. The runner (`src/db/migrate.ts`) and drizzle's `readMigrationFiles` follow the journal's order and `when`. They never look at `idx`, so the gap is harmless. The snapshot was generated by `drizzle-kit generate` and renamed from 0008 to 0009.
- **Web.** An optional `<input type="date">` in the ask box: empty by default, `max` today, and kept for follow-up questions. `useAsk` sends `lawAsOf` only when it is set. The answer card shows the note in the existing info-note style.

## Verification

- services/ai:
  - `test_retrieval.py`: three bail judgments, decided before the date, after it, and on an unknown date. With `law_as_of`, the later one is gone from both searches and the others and the statutes stay. Without a date (and with a date later than every judgment), the trace and passages are identical.
  - `test_answer.py`: `asOfNote` is present with `lawAsOf`, including on unanswerable answers and in Urdu, absent without it, and conforms to ai.v1.
- apps/api: the fake AI returns `asOfNote`. It is stored in `as_of_note`, returned on POST and on GET of the conversation (contract-checked), and absent without a date. The migration test covers 0009 down and up.
- apps/web: the date input is empty with a `max`, the date goes in the request body, and the note renders. With no date, the body has only `question` and no note shows.
- Query plans (EXPLAIN ANALYZE, synthetic 4,000 chunks): the dense branch uses the HNSW index plus a primary-key lookup per neighbour, and the sparse branch adds one primary-key lookup per matched chunk. Both are within the same time as before.
